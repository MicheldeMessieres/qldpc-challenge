# [[432,4,23]] — weight-5 bivariate bicycle code from arXiv:2610.06623v1 Table 3

## Direction & hypothesis

Target: the `unrestricted` x `weight-6` CSS cell, and inside it the thin
`k = 4` corner at large `n`. Screening arXiv:2610.06623v1 (Cruz-Benito,
"Large Language Model-Guided Discovery of Weight-Five Bivariate Bicycle
Codes") showed that every exact code the paper certifies at weight five was
either already on this board or Pareto-dominated by it, with one exception:
the rows carrying *interval* evidence rather than an exact certificate.
Those rows report no exact distance, so nothing on the board claims them, and
the paper's own arithmetic (`kd^2/n` at most 4.90) put them below the cell's
headline figures. The expectation was a narrow but real opening at `k = 4`,
`n` around 420-432, where the board had nothing.

This is a thin-cell record, not a strong one. `kd^2/n` is 4.90 where the same
cell already holds 30.5 (`[[672,20,32]]`).

## What was searched

No fresh search. The direction was to rebuild, verify, and Pareto-screen the
26 explicit presentations printed in Tables 3 and 6 of arXiv:2610.06623v1.

All 10 Table 3 (CSS) presentations were rebuilt with `research/kit/bb.py:build_bb`
and their `(n, k, w)` measured from the resulting matrices rather than read
off the paper; all 10 reproduced their claimed parameters exactly. The
replicated-component rows were then dropped, following the paper's own
connectivity analysis (409 of its 1,142 catalogue entries are disconnected,
and 73.1% of the classes with exact certificates are repeated components).

The 16 Table 6 (PBB) rows were screened on their published triples only. The
four-block layout in the paper's Eq. (4) did not reconcile with `n = 2*l*m`
under any standard block arrangement tried here, so no PBB presentation was
re-derived and none is claimed. Every one of them is dominated by the board
regardless.

Of the surviving CSS rows, seven are dominated by existing entries, two are
already on the board, and this one is Pareto-undominated.

## Evidence trail

The presentation: `l = 18`, `m = 12`, `A = 1 + x^4 y^3`, `B = 1 + x^5 y^11 +
x^10 y`, so `n = 2*18*12 = 432`.

- Rebuilt and measured: `n = 432`, `k = 4`, max check weight 5, one connected
  component (no replicated decomposition).
- Distance: the paper reports `5 <= d <= 23` (its `L4+I+W+B` evidence) and no
  exact certificate. This repository's own searches (`research/kit/surrogate.py:distance_rand_witness`,
  4 seeds x 6000 RIS trials, `pair_depth=16`, `gf2_fast` backend) independently
  returned weight-23 logicals on both sides and nothing lighter.
- Submitted as a witness-backed **upper bound**, `d <= 23`, on both sides. It
  is not certified exact and is not described as such.
- The trusted gate (`verify/validate_candidate.py`) returns `passed: true`,
  with `dedup` clean, refutation unrefuted over 8000 RIS trials, and
  `novelty.board_advancing: true` on `advances_by: ["d", "n"]`.

Dead end worth recording: the paper's other interval row, `[[420,4,5<=d<=22]]`
(two distinct presentations of it), shares this row's cell and is filed as a
separate `[[420,4,22]]` entry. The exact `[[432,4,10]]` presentation from the
same table is dominated eleven times over by entries such as `[[192,4,16]]`.

## Tools

Human-directed agent work (opencode CLI) rebuilding and screening published
constructions; `research/kit/bb.py` for construction, `research/kit/surrogate.py`
and the `gf2_fast` accelerator for the witness search, `verify/validate_candidate.py`
for the gate. Roughly 25 CPU-minutes of witness search on an n=432 code.
