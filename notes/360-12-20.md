# [[360,12,20]] — non-CSS perturbed bivariate bicycle (PBB) code, deep-MILP-incumbent upper bound

**Paper:** arXiv:2606.02418, "Evolutionary Discovery of Bivariate Bicycle
Codes with LLM-Guided Search" (non-CSS PBB catalog, Campaign 5 therein;
`code_id 30_6_0260`, `bliss_hash 5012d8bafff7fd2b`).

## Direction & hypothesis

Target: the general-stabilizer board's `unrestricted` x `weight-8` (and
looser) cells. Same PBB construction as the companion `[[144,12,12]]`
submission in this project (block-1 z-part `[C | D]` added to a CSS
bivariate-bicycle stabilizer matrix: `H = (A B | C D; 0 0 | B^T A^T)`).

## What was searched

Source: an LLM-guided evolutionary search (OpenEvolve) over 4-tuples
`(A, B, C, D)` at `(ell=30, m=6)`, with a 3-model ensemble (Claude Opus 4.6
34%, GPT-5.3-Codex 33%, Gemini 3.1 Pro 33%). Screened by `k`, isotropy, the
combined non-CSS gate, and a BP-OSD distance estimate (which, for this
code, suggested `d=44` -- see below for why that figure is not the one used
here).

## Evidence trail

`(ell, m) = (30, 6)`, `A = x^{13}y^4 + x^{22}y^3 + x^{22}y^2`,
`B = 1 + x^{13}y + x^5y^2`, perturbation `C = x^{13}y^3 + x^{22}y^3`,
`D = x^{13}y + x^{22}y` (0-indexed exponent pairs: `A=[[13,4],[22,3],[22,2]]`,
`B=[[0,0],[13,1],[5,2]]`, `C=[[13,3],[22,3]]`, `D=[[13,1],[22,1]]`).
`n = 2·30·6 = 360`, `k = 12`, max check weight 8.

**Why not the BP-OSD figure:** the source repository's own fast decoder
estimate for this code was `d_bposd = 44`, but this project's own
documented experience (`CLAUDE.md`: "BP-OSD overestimates distance by up to
12x for high-rate codes") is that BP-OSD alone is unreliable for codes like
this one, so a deep per-logical MILP pass was run instead
(`evaluation/distance_milp.py`, symplectic formulation, 7,201.6s wall time):
it found a feasible incumbent solution of weight 20 for **every one of the
24 logicals** (`logicals_incumbent: 24/24`), tightening the claim from 44
down to 20 -- but **0 of 24 were proven globally optimal** within the time
budget (`logicals_optimal: 0`, `trust_level: "TRUSTED"`, `d_is_exact:
False`, `milp_exact: False`). This is a real, materially tighter bound than
the raw decoder estimate, but it is an incumbent, not a certificate.

Independent re-verification in *this* repository, using a third, unrelated
distance-search method (not BP-OSD, not MILP): rebuilt the symplectic check
matrix via `evaluation/pbb_code.py:build_pbb_code`, then ran this repo's own
`cli/qldpc.py submit --dry-run` (RIS search, 20,000 trials, `gf2_fast`
accelerator at 1,000,000 trials). **Independently found d<=20**, matching
the deep-MILP incumbent exactly (and nowhere near the BP-OSD figure of 44) --
a third method landing on the same number as the second is modest
additional corroboration that 20 is a materially better bound than 44, even
though none of the three methods proves optimality.

Final claim here, honestly: `upper_bound`, `d<=20`.

## Dead ends

The naive BP-OSD estimate (`d=44`) for this code is exactly the kind of
overestimate this project has repeatedly found and documented; it is not
used as the submitted claim.
