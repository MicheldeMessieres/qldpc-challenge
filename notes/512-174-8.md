# [[512,174,8]] single-parity-check 3-fold product code

## Direction & hypothesis

Harvest item **M3** of the literature campaign in
[issue #2863](https://github.com/unitaryfoundation/qldpc-challenge/issues/2863):
arXiv:2505.06157 (Mostad, Lin, Rosnes, Lee, Lai), "Advancing Finite-Length
Quantum Error Correction Using Generalized Bicycle Codes". The paper prints one
code's parity-check matrices outright -- a single-parity-check (SPC) 3-fold
product code -- so the target was the `weight-8 x unrestricted` cell, where a
n=512, k=174, d=8 code sits well below the cell's current head.

## What was searched

No search in the usual sense: the paper gives the matrices directly. What I did
was screen **every instance named in the paper** against `codes/` on the
Pareto rule the verifier actually applies (`verify/validate_candidate.py` L245:
`b.n <= n and b.k >= k and b.d >= d and bw <= w`, non-strict on each axis, at
least one strict, restricted to the candidate's cell). Eight instances appear:

| claim | w | kd^2/n | on board | verdict at its own weight |
|---|---|---|---|---|
| `[[144,12,12]]` | 6 | 12.00 | yes | -- |
| `[[392,32,12]]` | 12 | 11.76 | no | dominated by 33 |
| `[[392,32,14]]` | 12 | 16.00 | no | dominated by 14 |
| `[[392,48,12]]` | 13 | 17.63 | no | dominated by 20 |
| `[[392,48,13]]` | 13 | 20.69 | no | dominated by 7 |
| `[[512,174,6]]` | 8 | 12.23 | no | dominated by 1 |
| `[[512,174,7]]` | 9 | 16.65 | no | dominated by 1 |
| **`[[512,174,8]]`** | **8** | **21.75** | **no** | **undominated** |

The three `[[512,174,*]]` codes are all beaten at w >= 10 by `[[470,192,12]]`
(w=10), so the whole item turns on whether the weight-8 one is real. It is.

## Evidence trail

`[[512,174,8]]`, confirmation ladder:

1. **Rebuilt from the paper's matrices**, not transcribed: `n = 512`,
   `k = 174` (as `rank(H_X) + rank(H_Z) = 169 + 169 = 338`), uniform row weight
   8 on both sides.
2. **20,000 RIS trials/side**, then a **2,000,000-trial accelerator pass**:
   weight-8 witness on the X side and on the Z side.
3. **Gate**: `passed: true`. `verify` clean, `refute` clean (`no lighter logical
   in 8000 RIS trials`, seed 1321537450), `dedup` reports no exact or
   Weisfeiler-Leman equivalent, and `novelty` returns
   **`board_advancing: true`** with `advances_by: ["d", "k", "n"]` and an empty
   `dominated_by`.

The distance claim is therefore a witness-backed **upper bound** `d <= 8`, not
an exact value, and it happens to agree with the paper's stated `d = 8`.

`advances_by` covering all three of n, k and d matters here: the board treats a
record whose only strict axis is `d` as a different and weaker kind of claim,
because both numbers are then witness-backed upper bounds. This one gains
outright, so it is a construction result rather than a search-depth artifact.

Near-miss candidates that collapsed, with numbers:

- `[[512,174,6]]` (GB#3, w=8) and `[[512,174,7]]` (GB#4, w=9): undominated only
  at w <= 8, and each is beaten by `[[470,192,12]]` at w=10. The paper's own
  GB constructions for these do **not** reproduce -- see dead ends.
- `[[392,48,13]]` (GB#2, w=13): undominated at w=6 alone, dominated by 7
  entries once the weight is honest. Filing it would mean building a worse code
  than the paper's and calling it theirs.

## Dead ends

**The paper's generalized bicycle codes do not reproduce, and this is worth
recording.** For `[[512,174,6]]` the paper gives both circulant polynomials and
Construction MMM explicitly (`H_X = [M1|M2]`, `H_Z = [M2^T|M1^T]`,
`M_i` = `l x l` circulants over `F2[x]/(x^l + 1)`, `l = 256`):

    M1 : 1 + x^73  + x^192 + x^234
    M2 : 1 + x^97  + x^144 + x^193

Built directly these give **k = 2**, not 174, with `w = 8` as quoted. The paper
gets k = 174 from a step it describes as "remove excess rows from H_X and H_Z to
ensure rank(H_X) + rank(HZ) = n - k". Deleting rows from `[M1|M2]` reduces the
*number* of checks but not the rank of the ones kept, and which 169 of the 255
independent rows survive is not specified -- so the resulting code is not pinned
down by the paper. The same holds for the `[[512,174,7]]` GB#4 pair and for
`[[392,48,13]]` GB#2. Conclusion: the SPC code is the only instance in this
paper that a reader can rebuild exactly, and it is the one filed here.

**A convention trap that cost real time.** My first transcription of the
polynomials dropped the powers and produced `k = 0`. Rather than trust the
number I checked the circulant convention against a code already on the board:
rebuilding `[[144,12,12]]` from its own recorded construction (orders (12,6),
`A = x^3 + y^2 + y`, `B = x^2 + x + y^3`) returns `n = 144, k = 12, w = 6`, which
confirms the convention and only then condemns the GB instances. Worth stating
because `n`, `k` and `w` can all look plausible while the code is wrong.

## Tools

Space Bunny Alpha 1.0 in the OpenCode harness, driving this repository's kit:
`research/spc_product.py` (builder, committed with this note),
`research/kit/css.py` for ranks and the CSS check, `research/kit/surrogate.py`
with the `gf2_fast` C++ accelerator (built via `make fast`) for the 2M-trial
pass, and `./qldpc submit` for packaging. Verification is
`verify/validate_candidate.py`, unchanged, via
`research/kit/coordination.py gate`. Screening against the board was done with a
throwaway script reimplementing the verifier's Pareto rule. Roughly 25 minutes of
wall clock, most of it the two search passes at n = 512.

## Reproduction

`research/spc_product.py` is the whole thing -- 9 Kronecker factors of `h` and
`I`:

```python
h = np.array([[1, 1]]); I = np.eye(2, dtype=int)
HX = np.vstack([kron(h,h,h,I,I,I,I,I,I),
                kron(I,I,I,h,h,h,I,I,I),
                kron(I,I,I,I,I,I,h,h,h)])
HZ = np.vstack([kron(h,I,I,h,I,I,h,I,I),
                kron(I,h,I,I,h,I,I,h,I),
                kron(I,I,h,I,I,h,I,I,h)])
```

`python research/spc_product.py` prints `n = 512  k = 174  max weight = 8`. The
matrices are as printed in arXiv:2505.06157 Sec. III-C, which attributes them to
its Ref. 18.
